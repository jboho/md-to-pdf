## Notes
- Release pipeline never executed (2026-09-12): `.github/workflows/release.yml` (on main since 2026-08-21, PR #6) triggers on `v*` tags, runs `npm run dist`, and publishes `dist/*.dmg` + `dist/latest-mac.yml` via `softprops/action-gh-release`. The design is correct; it has simply never fired. Verified against the live repo with admin permissions (so these are real zeros, not permission artifacts): **0** GitHub Releases (`gh api repos/jboho/md-to-pdf/releases` → length 0, drafts included), **0** Release-workflow runs, **0** repo secrets, **0** repo variables. Three distinct causes: (1) the only tag `v1.0.0` dereferences to `9901cd6` dated 2026-06-28, ~2 months *before* `release.yml` existed — tags do not trigger retroactively and re-pushing an existing tag is a no-op, so a fresh tag is required; (2) with no secrets, `CSC_LINK`/`CSC_KEY_PASSWORD` and the three `APPLE_*` vars all resolve empty, so `scripts/notarize.js` and `scripts/make-dmg.js` hit their documented no-op paths and the job still *succeeds* while emitting an ad-hoc unsigned build — a silent failure the workflow's own header comment (`release.yml:9-12`) warns about; (3) `jboho/md-to-pdf` is private, so the `electron-updater` feed in `src/main/updater.ts` has no credentials and will 404 even once releases exist. Consequence: the only signed artifact is `dist/mac-arm64/MD to PDF.app` on one local Mac, inside a gitignored `dist/` — one disk failure from gone.
- Local signing re-verified (2026-09-12): `dist/mac-arm64/MD to PDF.app` still checks out — `Authority=Developer ID Application: Jonathan Boho (72FBK9YTA3)`, hardened runtime (`flags=0x10000(runtime)`), `codesign --verify --deep --strict` valid and satisfies its Designated Requirement, `spctl -a -t exec` → `accepted, source=Notarized Developer ID`, staple valid. The `.dmg` carries a stapled notarization ticket but has no code signature of its own — that is by design (`scripts/make-dmg.js` notarizes and staples the image rather than signing it), so `spctl -t open --context context:primary-signature` reporting "no usable signature" on the `.dmg` is expected and not a defect; the stapled ticket is what Gatekeeper consumes.
- DMG pipeline fixed (2026-08-08): electron-builder's built-in `dmg` target fails on this toolchain with `hdiutil: create failed - Resource busy` — it runs `hdiutil create -srcfolder` directly against the live, fsevents/Spotlight-watched app bundle (reproduced across multiple runs, all 5 internal retries fail). Fix: `mac.target` is now `dir` (signed + notarized `.app` only, still via the `afterSign` notarize hook), and `scripts/make-dmg.js` assembles the `.dmg` from a clean `ditto` copy in a throwaway temp dir, then notarizes + staples the image (env-gated on the same `APPLE_ID`/`APPLE_APP_SPECIFIC_PASSWORD`/`APPLE_TEAM_ID`). `npm run dist` now runs `build → electron-builder --mac dir → node scripts/make-dmg.js` and completes end-to-end (exit 0), producing a notarized+stapled `dist/MD to PDF-1.0.0-arm64.dmg` (quarantined mount → `spctl -a` = `source=Notarized Developer ID`).
- better-sqlite3 packaging verified (2026-08-08): the native module loads and runs real queries in the signed+notarized build. Chain confirmed end-to-end against `dist/mac-arm64/MD to PDF.app`: (1) `better_sqlite3.node` is unpacked to `app.asar.unpacked/node_modules/better-sqlite3/build/Release/` (Mach-O arm64), and its JS deps `bindings` + `file-uri-to-path` ship inside the packed asar so `require` resolves; (2) the bundled Electron runtime is 35.7.5 / Node 22.16 / **ABI 133**, and the `.node` loads clean under it (probed via `ELECTRON_RUN_AS_NODE` requiring the module through the asar path — real INSERT/SELECT round-tripped, sqlite 3.49.2); (3) the `.node` is signed with the same `Developer ID Application (72FBK9YTA3)` cert + hardened-runtime flag, and `resources/entitlements.mac.plist` carries `com.apple.security.cs.disable-library-validation`, so the hardened runtime loads it; (4) launching the real GUI `.app` boots main+helper processes and freshly creates `~/Library/Application Support/md-to-pdf/md-to-pdf.db` (+WAL/shm) with all 3 migrations applied (tables: tasks, files, file_versions, css_themes, feedback). No packaging changes were needed — `asarUnpack: node_modules/better-sqlite3/**` in `electron-builder.yml` plus `externalizeDepsPlugin()` (keeps `require("better-sqlite3")` un-bundled) is the correct config.

- Native `better-sqlite3` must be rebuilt for Electron before `npm run dev` (`npm run rebuild`). Note: `electron-rebuild` is referenced by the `rebuild`/`postinstall` scripts but is not a declared devDependency — install `@electron/rebuild` or run `npx @electron/rebuild -f -w better-sqlite3`.
- M1 shipped: vitest suite (`npm test`, 36 tests) covering the task/file/version/cssTheme repositories, the version-tracking IPC flow (create → auto-version, edit → version-on-change-only, diff, restore), and multi-file batch orchestration (`generateBatch`) — status transitions, progress events, task completion, per-file errors, and cancellation. Testability seams: `setDbInstance`/`runMigrations` inject an in-memory DB (`test/helpers/db.ts`); `electron` is aliased to a mock in `vitest.config.ts` (`test/mocks/electron.ts`) whose `invokeHandler` drives real IPC handlers; `generateBatch` accepts an injectable `renderFile` so the batch loop is testable without a real PDF engine. Fixed a same-second ordering bug in `versionRepository.findByFile` (added `rowid DESC` tiebreaker).
- ABI dance for tests: `better-sqlite3` is a native module built for a single ABI. Tests run under Node — run `npm run rebuild:node` before `npm test`, and `npm run rebuild` (Electron ABI) before `npm run dev`. The two ABIs cannot coexist in one `node_modules`. This same native module is the main packaging risk for M2 — it must be rebuilt for Electron and correctly unpacked from the asar in the distributed app.
